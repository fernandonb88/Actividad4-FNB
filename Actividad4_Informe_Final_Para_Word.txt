2. ANALISIS DE RENDIMIENTO
============================================================

2.1 Metodologia

El archivo Actividad4/src/performanceChecks.ts evalua tres metricas mediante umbrales definidos:

- Tiempo de arranque: maximo 4,000 ms.
- Uso de memoria: maximo 200 MB.
- Frame rate: minimo 55 FPS.

El escenario documentado corresponde a un emulador Android API 33 con 4 GB de RAM, durante el arranque de la aplicacion y operaciones basicas de tareas.

2.2 Resultados

METRICA                 RESULTADO       UMBRAL              ESTADO
Tiempo de arranque      2,850 ms        <= 4,000 ms         Aceptable
Memoria pico            145 MB          <= 200 MB           Aceptable
FPS promedio            58 FPS          >= 55 FPS           Aceptable

La prueba automatizada verifica que el evaluador acepta valores dentro de los limites y reporta los tres problemas cuando recibe valores fuera de ellos.

Aclaracion metodologica: el archivo TypeScript evalua metricas recibidas, pero no mide por si solo la memoria o los FPS del dispositivo. Los valores anteriores corresponden al escenario de emulador documentado y deben presentarse como evidencia de ese escenario, no como una medicion generada automaticamente por Jest.

2.3 Cuello de botella identificado

Carga de listas grandes:

Durante la carga de mas de 100 tareas puede aumentar el uso de memoria y el trabajo de renderizado. Este comportamiento se registra como un area de mejora del escenario evaluado; no se afirma que se haya realizado una prueba con 10,000 usuarios.

Propuestas de mejora:

1. Implementar paginacion de aproximadamente 20 elementos por pagina.
2. Evaluar la virtualizacion de listas.
3. Medir nuevamente antes de aplicar React.memo en TaskCard.

Como segunda area de mejora, el arranque en frio de aproximadamente 2.85 segundos incluye la carga inicial del bundle. Se propone revisar el tamano del bundle y sus dependencias con un perfilador antes de aplicar lazy loading.

3. ANALISIS DE SEGURIDAD OWASP MOBILE TOP 10
============================================================

Se revisaron los servicios y flujos disponibles de la aplicacion. Se evaluaron tres areas del OWASP Mobile Top 10. El analisis realizado es estatico y no sustituye una prueba de penetracion, MobSF u OWASP ZAP.

AREA OWASP: M2 - ALMACENAMIENTO INSEGURO

Hallazgo:
No se encontro AsyncStorage ni almacenamiento de credenciales en el servicio revisado. Tampoco esta configurado expo-secure-store.

Estado y riesgo:
El flujo actual no persiste credenciales. El riesgo aumentaria si posteriormente se agregan tokens, contrasenas o claves.

Correccion propuesta:
Usar expo-secure-store para tokens y datos sensibles, no guardar contrasenas en texto plano y limpiar la informacion sensible al cerrar sesion.

AREA OWASP: M3 - COMUNICACION INSEGURA

Hallazgo:
El archivo src/services/taskService.ts utiliza la URL https://api.taskmanager.com. La prueba estatica comprueba que no se utilice una URL http://.

Estado y riesgo:
El codigo revisado utiliza HTTPS. El certificate pinning no esta demostrado en la implementacion actual.

Correccion propuesta:
Mantener HTTPS en todos los ambientes y evaluar certificate pinning antes de una puesta en produccion.

AREA OWASP: M1 - EXPOSICION DE DATOS EN LOGS

Hallazgo:
No se encontraron logs con contrasenas, tokens o claves en el codigo revisado.

Estado y riesgo:
No existe evidencia de exposicion de credenciales en el alcance analizado.

Correccion propuesta:
Mantener logs sanitizados y evitar registrar datos de autenticacion o informacion sensible.

Evidencia automatizada:
La prueba Actividad4/src/__tests__/securityAudit.test.ts lee el servicio real src/services/taskService.ts y comprueba el uso de HTTPS y la ausencia de almacenamiento inseguro en ese servicio.

Las pruebas adicionales de __tests__/security/ contienen escenarios de politicas de seguridad. No se presentan como evidencia de que AES-256, bcrypt, SecureStore o certificate pinning ya esten integrados.

4. PRUEBAS DE CONTRATO DE API CON ZOD
============================================================

El contrato esta definido en Actividad4/src/taskSchema.ts mediante TaskSchema.

Campos del contrato:

- id: cadena de texto no vacia.
- title: cadena de texto obligatoria, recortada y con minimo un caracter.
- completed: valor booleano.
- createdAt: fecha en formato ISO 8601.
- priority: enum opcional con valores LOW, MEDIUM o HIGH.

Archivo de pruebas:
Actividad4/src/__tests__/taskSchema.test.ts

Escenario 1 - Respuesta valida:
Se valida una tarea con id, titulo, completed booleano, fecha ISO y prioridad HIGH. El resultado esperado es valido.

Escenario 2 - Respuesta invalida:
Se valida un objeto con id vacio, titulo vacio, completed como texto, fecha invalida y prioridad URGENT. El resultado esperado es invalido.

La prueba utiliza safeParse y confirma ambos comportamientos. Resultado: 2 de 2 pruebas aprobadas.

Nota: el proyecto raiz tambien conserva otro contrato en __tests__/contract/taskApi.contract.test.ts, basado en el campo status. Para esta entrega la evidencia principal es el contrato de Actividad4, basado en el campo completed.

5. PIPELINE DE GITHUB ACTIONS
============================================================

Archivo:
Actividad4/.github/workflows/tests.yml

Activacion:
El workflow se ejecuta ante push y pull_request en las ramas:

- main
- develop
- QA
- master
- Actividad-4

Esto permite documentar el flujo academico develop -> QA -> master y validar directamente la rama de entrega Actividad-4.

Pasos configurados:

1. Checkout del repositorio con actions/checkout@v4.
2. Configuracion de Node.js 20 con actions/setup-node@v4.
3. Cache de dependencias npm.
4. Instalacion reproducible mediante npm ci.
5. Ejecucion de lint si existe el script correspondiente.
6. Ejecucion de la suite completa con npm test -- --coverage --ci.
7. Carga del directorio coverage/ como artefacto durante 30 dias.

El umbral minimo de cobertura del 70% esta configurado en el jest.config.js raiz, que es el archivo utilizado por el comando del workflow. Jest hace fallar la ejecucion si alguna metrica global queda por debajo del umbral.

El workflow implementa integracion continua y automatizacion de calidad. No realiza un despliegue automatico a produccion.

Evidencia de GitHub Actions:
La rama Actividad-4 muestra ejecuciones exitosas del workflow CI - Test Suite & Coverage Validation. Se debe adjuntar al PDF una captura de la ejecucion verde mas reciente.
